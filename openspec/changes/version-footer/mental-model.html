version-footer

Change delta — the running app learns its own version and shows it in a global footer.

Additive. No existing behavior changes; no requirement in another capability is modified.

The gap this closes

VERSION is the single source of truth and deploy.sh already passes it as --build-arg VERSION — but the Dockerfile never declared ARG VERSION, so Docker silently discarded it. The file is also not COPY'd into the image. Result: the deployed app could not name its own version.

Resolution chain

1 APP_VERSION env var, if non-empty — the production path, set by the image from the build arg.
2 repo-root VERSION file, trimmed — the dev path, so npm run dev shows the real version with no setup.
3 the literal dev — last resort; never fails startup.

path.resolve(__dirname, "..", "VERSION") is the same relative depth from src/ and from dist/, so one expression serves tsx and the built output alike. In the container that path is absent — correct, because step 1 already answered.

New unit: src/version.ts

  • resolveVersion(env, readVersionFile) — the precedence above, with the file reader injected so all three branches are testable without touching the filesystem.
  • formatVersion(version) — prefixes v only when the string starts with a digit. 2.8.0 → v2.8.0; dev → dev, not vdev.

Kept out of config.ts because that module runs loadConfig() at import and can process.exit(1) — pure functions in their own module stay unit-testable.

Render path

render() in src/views/render.ts is already the single funnel for every page: it enriches the data, renders the page template, then wraps it in layout.eta. Adding version to the enriched object gives every page the value in one edit, and layout.eta renders the new <footer> below <main>.

Formatting happens in render.ts, not the template — the view stays free of logic.

Why no catalog string

The footer's entire content is a version number or the literal dev. There is no prose to translate, so en.ts/es.ts are untouched and the footer renders identically in both locales. This follows the i18n rule rather than excepting it — the rule targets user-facing prose. A future label ("Version 2.8.0") or license line would go in the catalog then.

Touched files

  • Dockerfile — ARG VERSION=dev + ENV APP_VERSION in the runner stage, beside the existing ENV block.
  • src/version.ts (new) — resolveVersion, formatVersion.
  • src/version.test.ts (new) — precedence, trimming, fallback, prefix rule.
  • src/config.ts — APP_VERSION in the zod schema; appVersion on the resolved config.
  • src/views/render.ts — version added to the enriched template data.
  • src/views/layout.eta — new <footer class="app-footer">.
  • public/style.css — muted, mobile-first footer styling, normal document flow.

Not touched: deploy.sh (already correct), .env.example (APP_VERSION is deliberately build-time, not runtime config), any route, migration, or i18n catalog.
